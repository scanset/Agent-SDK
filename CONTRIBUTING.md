# Contributing to the ESP Agent SDK

Thank you for your interest in contributing to the **ESP Agent SDK**.

The Agent SDK is the reference scanner implementation for [Endpoint State
Policy (ESP)](https://github.com/scanset/Endpoint-State-Policy). It ships
both as a `esp_agent` CLI binary and as an embeddable Rust library that
external scanner authors can build on. Contributions are welcome from
engineers working on the scanner itself, the bundled CTN implementations,
documentation, build / CI infrastructure, or the embedding API surface.

This document outlines **how to contribute effectively** and what to expect.

---

## Project Philosophy

Before contributing, it helps to understand the guiding principles:

- **Declarative over imperative** — policies describe *what should be true*, not *how to check it*; the SDK preserves that boundary
- **Explicit contracts** — CTN behavior is defined through `CtnContract` declarations, not implicit assumptions in collectors
- **Security-first** — commands run in a sandboxed `SystemCommandExecutor` with explicit binary allow-lists; no shells, no `Command::new`
- **Determinism** — collectors return typed values; the engine produces a stable `replay_hash` over intent + contract + outcome
- **Tight local scope, broad gallery** — the SDK targets a local Linux host scanner by default; cloud / Windows / Kubernetes contracts live in the companion [Contract Library](https://github.com/scanset/Contract-Library) and get registered explicitly by consumers

If your contribution aligns with these principles, it likely fits well.

## Ways to Contribute

### 1. Bug Reports

If you find a bug:

- Open a GitHub Issue
- Include:
  - Agent SDK version / commit and ESP engine tag (`agent --version` once built; otherwise the `tag = "vX.Y.Z"` in `agent/Cargo.toml`)
  - Host platform and rustc version (`rustc --version`)
  - What you expected to happen
  - What actually happened
  - Minimal reproduction (ESP policy + command line, plus the JSON output if relevant)

Clear, reproducible bug reports are highly valued.

### 2. Documentation Improvements

Documentation contributions are always welcome:

- Clarifying existing docs in [`guides/`](guides/)
- Fixing inaccuracies in CTN spec docs under [`contracts/`](contracts/)
- Adding worked examples
- Improving onboarding or "how it works" explanations

If something confused you, it will confuse others.

### 3. CTN Contract Implementations

The Agent SDK ships a small RHEL 9 baseline (11 CTN types). Most new
contracts belong in the [Contract Library](https://github.com/scanset/Contract-Library)
rather than here — that's where the cloud, Kubernetes, M365, and Windows
implementations live.

Add a CTN here only when it's a true **local-host primitive** the SDK
should ship by default (e.g., a new local config-file format, a new
kernel facility). See [`guides/Contract_Development_Guide.md`](guides/Contract_Development_Guide.md)
for the full authoring workflow.

### 4. Performance and Architecture Improvements

Thoughtful refactors are welcome, especially around:

- The scanner's per-policy loop
- Memory usage during large batch scans
- Cleaner trait boundaries between collector / executor / contract
- Embedding-API ergonomics

Large architectural changes should start as an issue or discussion first.

### 5. Build / CI Infrastructure

Improvements to the Makefile, GitHub workflows, the pre-commit hook, the
SBOM pipeline, or the cross-compilation targets are welcome — these are
the load-bearing pieces that keep the supply-chain story honest.

## Development Setup

### Prerequisites

- Rust **1.92+** (the toolchain is pinned in `agent/rust-toolchain.toml`)
- Cargo
- Python 3 (for `make sbom`)
- Git **configured to sign commits** (see [Signed Commits](#signed-commits) below)

### One-time bootstrap

```bash
cd agent/
make install-tools     # cargo-audit, cargo-deny, cargo-cyclonedx, …
make install-hooks     # installs scripts/git-pre-commit into .git/hooks/
```

### Build

```bash
cd agent/
make build             # debug
make release           # release
make build-all         # native + Windows + Linux musl
```

### Run Tests

```bash
cd agent/
make test
```

### Formatting & Linting

```bash
cd agent/
make format            # auto-format
make lint              # strict clippy (matches CI)
```

### Before pushing

```bash
cd agent/
make ready             # format + sbom + lint + test
```

`make ready` mirrors what CI enforces. If it passes locally, CI will
pass.

## Pull Request Guidelines

When opening a PR:

- **Describe the problem** — What does this PR fix or improve?
- **Explain the approach** — Why this solution?
- **Keep changes focused** — One feature or fix per PR when possible
- **Add tests when applicable**
- **Update documentation if behavior changes** — especially the CTN spec
  docs under `contracts/` and the relevant section of `guides/`
- **Run `make ready`** before pushing

CI runs five gates and an aggregator: `lint`, `test`, `security`
(cargo-audit + cargo-deny), `sbom-freshness`, `build`. The branch
protection on `main` requires the aggregator `CI` check to be green.

Small, well-scoped PRs are easier to review and merge.

---

## Coding Guidelines

- Prefer explicitness over cleverness
- Avoid hidden behavior; collectors must not call `Command::new` or spawn
  shells — use `SystemCommandExecutor` with an explicit allow-list
- Favor readability over micro-optimizations
- Use existing patterns in the codebase (look at how a similar CTN does it)
- Keep error messages actionable and descriptive
- The strict clippy gate forbids `unwrap()`, `expect()`, `panic!`, and
  raw `[]` indexing — use `?` propagation and `.get()`-style fallible
  access

If you're unsure, consistency with existing code is usually the right
choice.

---

## Security Considerations

The Agent SDK intentionally avoids:

- Arbitrary shell execution (`Command::new` is on the `clippy.toml`
  disallowed-methods list)
- Unrestricted command invocation (every collector declares its
  binary allow-list)
- Runtime policy mutation
- Network egress outside of explicitly declared probe CTNs

If you believe a change could impact security:

- Call it out explicitly in the PR
- Explain the threat model
- Explain why the change is safe

Security issues should not be reported via public issues. Please email:
**curtis@scanset.io**

## Signed Commits

The Agent SDK is delivered into federal-compliance contexts and requires
a verifiable authorship chain. **All commits on `main` must be signed.**
The `Require signed commits` branch-protection rule is enforced on
`main`; unsigned commits will be rejected at PR merge.

### One-time setup (SSH, simpler)

If you already have an SSH key on GitHub, signing with it is the easiest
path:

```bash
git config --global gpg.format ssh
git config --global user.signingkey ~/.ssh/id_ed25519.pub
git config --global commit.gpgsign true
git config --global tag.gpgsign true
```

Then add the same SSH key under **"Signing key"** in your GitHub
settings — this is a separate entry from the "Authentication key" slot,
even if it's the same key material:
<https://github.com/settings/keys> → "New SSH key" → set Key type to
**"Signing Key"**.

### One-time setup (GPG)

If you prefer GPG:

1. Generate a signing key if you don't have one:

   ```bash
   gpg --full-generate-key   # RSA 4096 or Ed25519 recommended
   ```

2. Export the public key and add it to your GitHub account:

   ```bash
   gpg --armor --export YOUR_KEY_ID
   # paste into https://github.com/settings/keys → "New GPG key"
   ```

3. Configure git to sign by default:

   ```bash
   git config --global user.signingkey YOUR_KEY_ID
   git config --global commit.gpgsign true
   git config --global tag.gpgsign true
   ```

### Verifying it worked

After a commit:

```bash
git log --show-signature -1
```

The commit should show `Good signature from "Your Name <email>"`. On
GitHub, the commit listing displays a green **Verified** badge.

### Release tags

Maintainers cutting a release tag (`vX.Y.Z`) must sign the tag — this is
the trust root that downstream consumers verify against the release
artifacts. Tag signing is enabled by `tag.gpgsign = true` above.

```bash
git tag -s vX.Y.Z -m "Release vX.Y.Z"
git push origin vX.Y.Z
```
